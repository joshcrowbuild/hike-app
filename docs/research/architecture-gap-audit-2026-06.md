## Executive summary — what else did we forget

1. **The commons forked write (Rule #8 / Thread T3) is unbuilt — and marked ✅ in the decision log.** The single most-emphasized "build now" item (`decision-log §12, §32`) does not exist in `create_episode()`; the ✅ at decision-log lines 265/282 is **wrong memory**. Every episode ingested now is a permanently-lost de-identified contribution. This is the headline miss: a load-bearing thread assumed-done, exactly the device-seam failure class.
2. **The owned-node WRITE path bypasses the access-control choke point.** Rule #4's "single path to owned data" governs only reads (`ScopedSession`); `belief_update.py` and `ingest_episode.py` write Episode/Belief/PhysicalProfile via a raw unscoped runner with hand-typed `owner_id` clauses. The fuzz test can't see the write path. Cross-user write safety is convention, not seam.
3. **`viewer_id` is client-supplied and unauthenticated, and the private overlay will egress to the cloud judge.** `PlanRequest.viewer_id` is a forgeable request field; and `build_runtime` resolves the judge with no `touches_private_overlay` flag, so Epic-003's personal-context block will be sent to Anthropic the moment it lands. Two latent holes in the same private-by-default rule, both invisible until Epic-003 ships.
4. **Both corpus sources and live adapters are hardcoded per-source where a registry/seam was specified.** `ingestion/sources/*` (Stage 3 §9) was never built — `run_pipeline()` names osm/nps/usfs literally with OSM forced as spine; `verifier.build_probes()` hardcodes five adapters with no `LiveAdapter` contract. A second weather/AQI/streamflow source, or a non-OSM-spine region, is a rewrite, not a config line. The device-seam miss, replicated on both halves of the data plane.
5. **`Episode.date` is never written** — the field every personalization query filters on. `create_episode` never sets `e.date`; Epic-003 filters `e.date > date() - duration('P18M')`. Date-filtered retrieval silently returns zero episodes; the memory layer looks empty after trips are logged, undetectable until Stage-7 eval shows no memory effect.

CRITICAL count: 6. Total findings after dedup: 18.

## CRITICAL findings

### C1 — Commons forked write (T3 / Rule #8) is unbuilt, and falsely marked ✅
**What.** The de-identified commons fork is the most-repeated "build now" commitment in the project (`decision-log §12` line 124: *"Build now: only the forked write"*; §32 lines 265/282; `workplan T3`; `Stage 5 §6`; `Stage 6 §6.2 / S6-10`). It does not exist. `grep -rn "CommonsObservation|writer_hash|sever|capability_band"` over `ingestion/ orchestration/` returns nothing; the only hit anywhere is the **reserved-label comment** in `graph/schema.cypher`. `ingest_episode.py::create_episode()` writes the Episode (with raw `pace_on_grade`, distance, and full start/end lat-lon captured in `parse_fit`), wires `Person-[:DID]->Episode`, enqueues the belief update, and stops. Worse: `decision-log.md` lines 265 and 282 both mark this ✅ with concrete claims ("written in same transaction as Episode; person link severed; 250m endpoint trim; raw pace substituted with 4-band capability label") — all false. `decision-log-additions-proposed.md §36` documents `create_episode()` in detail and is silent on the omission.
**Why it matters.** Two compounding costs. (1) The commons thesis depends on accreting **from day one** while dormant; de-identification must happen at write time, so contributions can never be backfilled — every episode ingested now is a permanent hole. (2) The ✅ is *wrong memory* (CLAUDE.md: "wrong memory is worse than none"): a future builder reads §32, builds Stage 9 aggregation on an empty store, and finds months of zero accretion. `epic-004 AC-4.4` already names "the existing commons path" as a downstream dependency it must not change — it is built atop a phantom. Stage 7 §7 promises a *zero-tolerance* privacy invariant asserting severance fires; that test would vacuously pass against absent code — a false guarantee.
**Where.** `ingestion/ingest_episode.py` (`create_episode`, no fork); `graph/schema.cypher` (reserved comment only); `docs/decision-log.md §12, §28, §30, §31, §32` (false ✅ at 265/282); `docs/workplan.md T3`; `Stage 5 §6`, `Stage 6 §6.2`, `Stage 3 §6.6/§8`; `epic-004 AC-4.4`; no commons test exists.
**Action — epic + fix (high-leverage, mostly small).**
1. **Immediately demote** decision-log §32 (lines 265/282) from ✅ to 🔶 "designed, not built." The false ✅ is the dangerous part — do this first, regardless of the rest.
2. File a **Commons Fork epic** (none exists) as a *Phase-1 dependency of the episode pipeline*, not Stage 9. The write accretes now; aggregation is later.
3. Add the forked `CommonsObservation` write **inside `create_episode()`'s existing transaction**: no `:Person` edge, store `writer_hash` for revocation, 250m endpoint trim, substitute raw pace with the capability band.
4. Land the Stage-3 §8 / Stage-7 §7 structural privacy test (no `:Person` reachable from `:CommonsObservation`; trim fires; raw track absent) **before** more episode-write code lands.

### C2 — The owned-node WRITE path bypasses the ScopedSession choke point
**What.** `graph/load.py` asserts ScopedSession is *the* choke point but scopes it to "reads of owned nodes." The personal-overlay **writes** go through a raw runner: `belief_update.py` takes `Runner = Any` and writes Episode/Belief/PhysicalProfile with hand-rolled Cypher; `ingest_episode.py` builds `make_runner(neo_session)` (fully unscoped) to drain belief updates, and `create_episode` calls `session.run(...)` directly with manually-typed `owner_id = $owner` filters. The sanctioned `graph.queries.owner_scope()` helper is used by exactly **one** read stub and by **none** of the code that actually writes owned nodes.
**Why it matters.** decision-log line 240 commits to `scopedQuery` as "the only path to owned data," and the property-based fuzz test is meant to prove no ungranted node leaks — but it only covers the `queries.py`/ScopedSession read path and *cannot see the raw-Runner write path at all*. As grants and multiplayer (Stage 8) land, one writer that forgets the inline `owner_id` clause (a shared-Belief MERGE, a party-profile write keyed only by `party_key`) silently creates or overwrites another member's node, with no seam or test to catch it. Same class as the device-seam miss: a cross-cutting invariant implemented as scattered hand-typed clauses instead of one enforced seam.
**Where.** `orchestration/belief_update.py` (esp. `_write_pace_belief` ~182-242, `process_episode` ~248); `ingestion/ingest_episode.py` (`create_episode` ~152-225, `make_runner` drain ~273-280); `graph/load.py`; `graph/queries.py` (`owner_scope`, unused by writers); `docs/decision-log.md:240`.
**Action — seam.** Extend ScopedSession to cover writes: a `run_write` that injects `$viewer_id` and refuses an owned-label MERGE/SET unless an owner-scoping clause is present. Route `belief_update` + `ingest_episode` through it. Make `graph.queries` the only place owned-node Cypher (read **and** write) is authored, and point the fuzz test at the write builders.

### C3 — `viewer_id` is client-supplied and unauthenticated
**What.** `PlanRequest.viewer_id` is a plain request field defaulting to `"anonymous"` (`api/schemas.py:15`); `api/app.py:130` passes `request.viewer_id` straight into `build_runtime → scoped_session` with zero authentication. Any caller can POST `{"viewer_id": "mem:josh", ...}` and ScopedSession will faithfully scope to Josh's overlay. The graph layer does exactly what it's told; nothing establishes that the caller *is* the viewer.
**Why it matters.** Rule #5 + decision-log:131-134 make the auth boundary == the shared/private boundary. Today no overlay is exposed over HTTP so the hole is latent — but **Epic-003 wires personal beliefs/episodes into `plan()` over this same unauthenticated endpoint.** The moment it lands, the access-control seam everyone trusts leaks every user's overlay to anyone who guesses a member id. The seam protects against forgetting a WHERE clause, not against a forged identity, and no doc states where `viewer_id` becomes trustworthy.
**Where.** `api/schemas.py:15`; `api/app.py:125-134`; `orchestration/engine.py:158-168` (`build_runtime` trusts `viewer_id` verbatim); `docs/decision-log.md:131-134`.
**Action — spec.** Record an explicit auth-seam decision: `viewer_id` MUST derive from an authenticated session/token, never the request body. Until auth exists, hard-fail any request whose `viewer_id != "anonymous"` (or gate behind a shared dev secret), and document `build_runtime`'s contract as "viewer_id is already authenticated."

### C4 — Private overlay egresses to the cloud judge
**What.** `registry.resolve()` *has* the privacy seam: `touches_private_overlay=True` forces the local provider (`registry.py:50-65`). But `engine.build_runtime` calls `resolve("extract", settings)` and `resolve("curate", settings)` **with no flag** (`engine.py:161-162`), so both default to `False` and use the tier's configured provider — which can be Anthropic. Epic-003 then injects the assembled personal-context block (capability pace, prior-visit history, inferred preference beliefs) as the `profile=` argument into that exact judge call. Net: the overlay is sent to the cloud precisely when Rule #5 says it must stay local — and the block is even labelled "[PERSONAL CONTEXT — private, not for disclosure]" while being handed to a cloud model.
**Why it matters.** Rule #5 and decision-log §13 routing exist to keep the overlay on-device. The seam is built and *looks* honored; the one call site that will carry overlay data doesn't request it. Default `False` + `build_runtime` not knowing whether context is non-empty = the first Epic-003 commit silently ships personal data to Anthropic, no error, no test failure.
**Where.** `orchestration/engine.py:161-162`; `orchestration/providers/registry.py:50-65`; `docs/epics/epic-003-context-assembly.md`; `CLAUDE.md` rule #5; `decision-log §13`.
**Action — spec / seam.** Make the personalized-ranking judge resolve with `touches_private_overlay=True` whenever a non-anonymous viewer (or non-empty context) is in play, **or** split the judge into anonymous-cloud vs. personalized-local. Add an Epic-003 AC asserting the personalized `rank_ids` call resolves to a local provider, plus a test that fails if overlay context reaches a cloud provider.

### C5 — Corpus sources hardcoded; the `ingestion/sources/*` seam (Stage 3 §9) was never built
**What.** `ingestion/pipeline.py::run_pipeline()` is written against exactly three named sources: separate `osm_features`/`nps_features`/`usfs_features` vars, literal `if "osm" in active_sources` blocks, direct `fetch.osm/nps/usfs` imports, and a CLI `--source choices=["osm","nps","usfs"]`. Conflation is bolted to the trio: matches are pairwise with OSM hardcoded as feature-set `a` (the spine), and the load loop special-cases OSM as canonical. `ingestion/fetch/` has **no base contract** — the three `fetch()` functions just happen to return `list[Feature]`. This contradicts `Stage 3 §9` (`ingestion/sources/*` adapters); that directory is **confirmed absent**.
**Why it matters.** A new corpus source (USGS NTD corroboration per §5, PAD-US manager join, 3DEP elevation, RIDB permits, a future regional trail dataset) is a rewrite of `run_pipeline` + the conflation wiring, not "one adapter + config." Stage 3 §7 already calls for enrichment joins that have nowhere to plug in. The OSM-as-spine assumption forces a code change for any agency-authoritative region. As coverage expands (§2 "many regional runs"), this compounds per source.
**Where.** `ingestion/pipeline.py` (`run_pipeline` + load loop); `ingestion/conflate/match.py` (OSM forced as `a`); `ingestion/fetch/` (no base); `Stage 3 §9` (never built).
**Action — epic.** Introduce a `Source` adapter protocol (`fetch(bbox|polygon)->list[Feature]`, plus `name`, `role` ∈ {spine|conflate|enrich}, `authority_tier`) under `ingestion/sources/` as §9 specified, with a registry the pipeline iterates. Make `run_pipeline` loop over enabled sources and conflate non-spine sources against the *configured* spine generically. Separate enrichment adapters (3DEP/PAD-US/RIDB) as a second kind so §7 has a home.

### C6 — Live-data adapters hardcoded; no `LiveAdapter` contract or registry
**What.** `verifier.py` hardcodes `from orchestration.adapters import airnow, firms, nws, ridb, usgs_water` and a hand-written `build_probes(settings)` with a per-source `if settings.<x>_key:` branch and inline `partial(...)` to reconcile mismatched signatures (`usgs_water.fetch` keyless, `nws.fetch` needs `user_agent`, `ridb.fetch` needs `api_key`). Unlike the model-provider seam — which has a real `ModelProvider` contract, a config-driven `registry.py` resolving by name, and two interchangeable adapters — `adapters/base.py` defines only the `VerifiedFact` data shape, **no adapter interface**. There is no `ADVENTURE_LIVE_ADAPTERS` config list and no way to register an alternate provider for the *same* condition kind.
**Why it matters.** The exact device-seam miss, one layer over. A weather fallback (Open-Meteo/Tomorrow.io when NWS is down), a second AQI/streamflow source, a non-US fire feed — each requires editing `build_probes`, a Settings field, an import, another `partial`. "Weather" is permanently == NWS. Stage 4 §5 frames each adapter as *degrade-and-disclose on outage*, but a single hardcoded provider per kind means an NWS outage = no weather, with no swap path. Source-or-silence (#1) makes redundant providers especially valuable; the absent seam blocks them.
**Where.** `orchestration/verifier.py` (`build_probes` 26-37); `orchestration/adapters/base.py` (`VerifiedFact` only); contrast `orchestration/providers/base.py` + `registry.py` (the seam done right); `Stage 4 §5`.
**Action — seam.** Add a `LiveAdapter` protocol in `adapters/base.py` (`fetch(lat,lon)->VerifiedFact|None`, plus `kind` and a `from_config(settings)` factory) and `adapters/registry.py` mirroring `providers/registry.py`, **keyed by condition-kind** so multiple providers back one kind (primary + fallback). Drive selection from an `ADVENTURE_LIVE_ADAPTERS` config list. Fold the Router/drive-time adapter (M5) into the same registry.

## MODERATE findings

### M1 — `Episode.date` is never written
**What.** `Stage 6 §1.3` maps FIT `start_time → Episode.date` and `Stage 5` makes `date` first-class. But `ingest_episode.py` never extracts `start_time` (it isn't even a field on `FITSummary`) and `create_episode` never sets `e.date`. Every episode is date-less. Epic-003 AC-3.2 filters `e.date > date() - duration('P18M')` and `ORDER BY e.date DESC`; `PhysicalProfile.last_episode_at` is sourced from it and is also never set.
**Why it matters.** Once context assembly is built against this, every date-filtered retrieval silently returns zero episodes — the personalization layer looks empty after trips are logged. Invisible until Stage-7 memory-on/off eval shows no memory effect. Date is also needed for decay/supersession (Stage 5 §3).
**Where.** `ingestion/ingest_episode.py` (`FITSummary`, `parse_fit` session block, `create_episode` MERGE); `Stage 6 §1.3`; `Stage 5 §4`; `epic-003 AC-3.2`.
**Action — fix.** Add `start_time` to `FITSummary`, parse it, write `e.date = date($start_date)`, set `PhysicalProfile.last_episode_at` in `belief_update`. Add a test that a date-filtered query returns the just-ingested episode.

### M2 — Episode MERGE keyed on synthesized id, not `(watch_activity_id, owner_id)`
**What.** `Stage 6 §3.1` / S6-6 specify the idempotent MERGE keyed on `(watch_activity_id, owner_id)`, with `watch_activity_id` namespaced `garmin:{id}` / `coros:{id}` so an exact re-ingest is a structural no-op. Code instead MERGEs on `episode_id = f"ep:{owner_id}:{watch_activity_id}"`, and `watch_activity_id` is derived from the **FIT filename** (`file:{path.stem}`), not the vendor activity id. Re-downloading the same activity to a different filename → different stem → duplicate Episode.
**Why it matters.** The dedup design rests on the namespaced activity id being the key. The poller (Epic-004) cannot satisfy AC-4.3 ("re-run is a structural no-op") without rework; duplicates double-count `corroboration_n`, inflating belief confidence past the N=3 floor on a single re-ingested trip (it folds twice into the EWMA pace belief).
**Where.** `ingestion/ingest_episode.py` (`watch_activity_id=f"file:{path.stem}"`, `episode_id` MERGE key); `Stage 6 §3.1`, S6-6, §2.2; `epic-004 AC-4.3`.
**Action — fix.** MERGE on `(watch_activity_id, owner_id)`; source `watch_activity_id` from the vendor's namespaced id (available once the device seam lands). Flag the filename fallback as dev-only. Land jointly with the Garmin-fragility work (re-auth/health signaling, AdapterHealth) so the seam's mitigation story is real, not design-only.

### M3 — No condition caching / TTLs — the "already architected" cost lever is absent
**What.** `Stage 4 §4` specifies per-source TTL caching (NWS ~10m, USGS ~15m, AirNow ~60m, FIRMS ~10m, RIDB minutes-hours) keyed by resolution ids; §8 lists it as one of four cost levers "already architected." In code the TTLs survive only as **docstring comments**. `verifier.verify()` calls every probe live for every candidate on every `plan()` run, no cache.
**Why it matters.** `plan_from_origin` verifies up to K candidates per feed render; with no cache, re-opening the feed re-hits every live API K times. AirNow caps at 500/hr, FIRMS at 5000/10min — the architecture explicitly relies on TTLs to stay under fair-use, and the §8 cost spike *assumes* "re-open within TTL re-verifies nothing." Both the estimate and the budget the spike produces are wrong without it.
**Where.** `orchestration/verifier.py`; `orchestration/adapters/{nws,usgs_water,airnow,firms,ridb}.py` (TTLs in docstrings only); `Stage 4 §4`, §8.
**Action — fix (or explicit defer).** Build a small TTL cache keyed by `(source, rounded lat/lon | site_id)` wrapping the probes, TTLs from the §4 table. Naturally co-located with the live-adapter registry (C6). If deferred to the spike, note the deferral in the Stage-4 doc so the cost number isn't read as architected-and-built.

### M4 — No geocoding seam
**What.** `engine.plan()`/`plan_from_origin()` take `origin: tuple[float, float]`, and `PlanRequest` passes `lat`/`lon` straight through. There is no geocoding step anywhere — no module, adapter, or config — to turn a typed place/address into coordinates. `grep geocod/nominatim` hits docs only.
**Why it matters.** Geocoding is unavoidable for a real product (a human supplies a place, not a lat/lon). Added under deadline it'll be dropped inline against whatever provider is handy — the next single-vendor hardcode. Geocoding providers differ sharply in license/ToS (Nominatim usage policy vs. commercial Google/Mapbox), so it's precisely the axis that must be swappable from day one. It's also reverse-geocoding territory for watch-derived "near me" flows.
**Where.** `orchestration/engine.py` (origin tuple); `api/app.py` (lat/lon passthrough); no geocoder module exists.
**Action — spec.** Define a thin `Geocoder` seam (`geocode(query)->(lat,lon,confidence,source)`, `reverse(lat,lon)->place`) behind config **before** the first geocoding call, so the first impl is an adapter. Same shape as the live-adapter seam; source-or-silence applies to the resolved origin.

### M5 — Valhalla routing is a single hardcoded adapter, not behind a `Router` seam
**What.** `adapters/valhalla.py` is the only routing/drive-time impl; its request shape (`sources_to_targets`, `costing='auto'`) is Valhalla-specific and there's no routing abstraction. It's excluded from the Verifier (deferred to ranking) yet ranking doesn't call it either — drive-time is computed **nowhere** in the live pipeline today, despite Stage 4 §3-4 making drive-radius a primary filter and §8 a cost lever.
**Why it matters.** Drive-time/isochrone is swap-prone: self-hosted Valhalla vs. OSRM vs. GraphHopper vs. hosted differ in shape and op-cost. Referenced by module name with no `Router` contract, a swap (or a hosted fallback) rewrites every call site. Lower severity only because there's one call path and it isn't wired in — which means the seam is cheap to introduce *now*, before call sites multiply.
**Where.** `adapters/valhalla.py`; `verifier.py` (explicitly defers it); `engine.py` (no drive-time call); `Stage 4 §5`; `epic-005`.
**Action — seam.** When wiring drive-time into ranking, introduce a `Router` adapter (`drive_time(origin,target)->VerifiedFact|None`) behind config, not a direct `valhalla.fetch` import. Fold into the live-adapter registry (C6).

### M6 — Secrets are plaintext `.env`; the "real secrets store from the first commit" rule is doc-only
**What.** Rule #10, decision-log §14 ("a real secrets manager / encrypted store, never in the repo or plaintext config … security-critical from the first commit"), §27, and workplan T1 all promise a day-one secrets *store*. Built: plaintext `.env` documenting `GARMIN_PASSWORD`, `ANTHROPIC_API_KEY`, etc.; `config.py` reads `os.environ`; README says "Secrets live only in `.env`." No secrets-manager abstraction/seam exists — no interface, no Vault/SOPS/KMS adapter, not even a stub. The stated bar ("never in plaintext config") and the artifact (plaintext config is the only mechanism) disagree.
**Why it matters.** §23 lists secrets handling under "Must be rigorous before code (expensive to retrofit)." Garmin creds are a full-account login, the most sensitive secret. Without even a thin `SecretProvider` seam, every call site (`config.py`, the future Garmin poller, `watch_sync.py`) hardcodes `os.environ` access, so moving to a real store later touches every consumer — the device-seam shape, one layer down.
**Where.** `CLAUDE.md` rule #10; `decision-log §14, §27, §23`; `workplan T1`; `.env.example`; `orchestration/config.py`; `README.md`.
**Action — seam.** Introduce a thin `SecretProvider` interface (`get_secret(name)`) with an env-backed default adapter now, so `.env` stays the dev backend but call sites never read `os.environ` for secrets directly. Mirrors the provider seam done right. **At minimum**, reconcile the docs: either soften the rule to "env for local dev, store for deploy," or build the seam — right now the rule and the artifact contradict.

### M7 — Retention / deletion / backup policy (§14) is orphaned
**What.** decision-log §14 commits to right-to-delete for a member's private graph, a deletion path for commons contributions, retention windows per data type, and scheduled graph backups ("episodic memory is irreplaceable personal history"). `grep retention/deletion/backup/right-to-delete` across all stage docs, epics, process docs, and code hits **only** decision-log + workplan. No stage doc designs it, no epic schedules it, no code implements it. The commons-deletion path is doubly load-bearing because §30/§31 disclose post-aggregation deletion is unrecoverable — the `writer_hash` revocation hook (the deletion mechanism) isn't built (see C1) and the policy isn't written.
**Why it matters.** Right-to-delete becomes a likely legal/privacy obligation the moment there's a second real user (Carter, Phase 2), and is far cheaper if write paths anticipate it. Backup of a local-only Neo4j: the first disk failure loses irreplaceable history. Unscheduled (not even an open epic) → surfaces as a scramble at the Phase-2 boundary.
**Where.** `decision-log §14, §18, §27`; `workplan T1`. Absent from all `stage-*.md`, `epics/*`, `process/*`, and code.
**Action — spec.** Add retention/deletion/backup to a stage doc (right-to-delete → Stage 8 multiplayer/privacy; backup cadence → Stage 0/T1) so the ❓ items resolve before Carter onboards. At minimum file a tracking epic. Design the commons-deletion path jointly with the `writer_hash` fork (C1) so write + revoke land together.

### M8 — Corroboration count is owner-unscoped
**What.** `_write_pace_belief` recounts corroboration via `size([(b)-[:DERIVED_FROM]->() | 1])` and promotes confidence 0.3→0.7 at n≥3. The `DERIVED_FROM` target is unconstrained — it counts every episode edge on the belief node regardless of episode `owner_id`. Contained today only because `belief_id` is namespaced per owner; the count itself has no owner guard, while the ABOUT/Episode matches one line away **do** carry owner — this query is the odd one out.
**Why it matters.** Rule #7 ties confidence to corroboration; Rule #2 makes the floor the gate for injecting an inferred belief into context (Epic-003 AC-1.2). If Stage 8 introduces a shared/party-level belief node (party profiles already exist, schema:314), an unscoped count lets one member's hikes push a belief across the floor for another — confidence becoming a function of ungranted substrate, violating the floor semantics and Rule #5.
**Where.** `orchestration/belief_update.py:223-232` (unscoped `size()`); contrast the owner-scoped matches around it; rules #2/#5/#7.
**Action — fix.** Scope the recount to owner-matched episodes (count only `DERIVED_FROM` to Episodes with `owner_id = $owner`), routed through the owned-node read builder (C2) so the invariant is enforced, not incidental to id-namespacing.

### M9 — No owned-label manifest / DB invariant — a forgotten scope clause fails open
**What.** `schema.cypher` enforces id-uniqueness and comments "every owned node carries owner_id," but Neo4j Community has no existence/NOT NULL constraint and there's no label/marker distinguishing "owned" from "world" nodes. `owner_scope()` filters `owner_id = $viewer_id OR owner_id IN $granted_ids` — a node written *without* owner_id matches neither branch (fails safe on read), but any query that *forgets* `owner_scope` returns every owner's nodes (fails open), and nothing structural flags the label as owned.
**Why it matters.** The whole model rests on "owned ⟺ has owner_id ⟺ author remembered owner_scope." There's no machine-checkable definition of which labels are owned, so the fuzz test/lint can't enumerate them to verify coverage. As Stage 8 adds the severed-link `:CommonsObservation` and shared/derived nodes, the owned/unowned/derived trichotomy gets subtle, and a new owned-but-unmarked label reads as public — structural debt that compounds exactly when multiplayer makes leaks consequential.
**Where.** `graph/schema.cypher:157-195`; `graph/queries.py:16-18`; `decision-log:240`.
**Action — spec.** Define the set of owned labels in one place (a manifest the scoping seam *and* tests import), add a CI check that every Cypher touching an owned label carries `owner_scope`, and an ingest-time invariant + test that no owned node is written without `owner_id` (Community; add existence constraints where Enterprise is available). Pairs with the write-path seam (C2) and the Epic-003 redirect (see M-note below).
> Epic-003 note: `epic-003-context-assembly.md` plans a new `orchestration/context_assembly.py` authoring inline `owner_id = $viewer_id` Cypher (a *third* copy of the scope clause, outside `graph/`). Redirect it to add read builders to `graph/queries.py` using `owner_scope()`, called through ScopedSession — keep all owned-node Cypher in one place so one fuzz test and one grants change cover everything. (Folded here rather than as a separate finding; same root as C2/M9.)

### M10 — Commons capability-band schema conflicts across Stage 5 / Stage 6
**What.** Two docs define the 4 commons bands **differently**. `Stage 6 §6.2` (S6-10): easy (≤12) / easy-moderate (12-16) / moderate (16-20) / strenuous (>20) min/km. `Stage 5 §6` (S5-11): easy-moderate / moderate / moderate-strenuous / strenuous — a different *label set*, not just different cut points. Both are 🔶 "tune in Stage 9," but the band substitution is the privacy primitive that strips raw pace before the commons write.
**Why it matters.** When the fork is built (C1), the implementer picks one of two contradictory definitions; later reconciliation re-buckets contributions, unrecoverable once aggregated. Inconsistent bands across the corpus-side and episode-side writers fragment the k-anonymity counting — the same capability lands in different buckets by code path, weakening the k-floor that doubles as the confidence floor (§7). The 🔶 is being read as "defer the value" when the disagreement is about the band *schema*.
**Where.** `Stage 6 §6.2` (S6-10); `Stage 5 §6` / `decision-log §30` (S5-11); `decision-log §31`. No code yet.
**Action — spec.** Reconcile into one canonical table before building the fork; make it a single shared constant both writers import. Keep the 🔶 on the numeric cut points; resolve the label-set disagreement now — schema decision, not tuning.

### M11 — Readiness filter (Epic 007) specified across three stages, zero impl, party composition undefined
**What.** The readiness filter is decided (`decision-log §10` user-toggled FILTER; `Stage 5 §5`/S5-9 filter-only-never-a-belief; `Stage 6 §5.3` JIT Curator parameter; `device-seam §2` `ReadinessSignal` type). Epic-007 is referenced by epic-004 as a consumer but **doesn't exist** in `docs/epics/`.
**Why it matters.** Epic-004 (device seam) names Epic-007 as the readiness consumer of `fetch_readiness`/Capabilities; building the seam without the consumer's contract means `ReadinessSignal` is produced into a void and the "degrade-and-disclose when no readiness API" promise (DV-4) has nothing to degrade. Built later under pressure, "gates on the less-recovered" gets invented ad-hoc; wrong party composition risks surfacing a trail one member isn't recovered for — readiness is a Curator *hard* filter, so this is safety-adjacent.
**Where.** `orchestration/curator.py`, `engine.py`, `api/` (no readiness); `docs/epics/` (no epic-007); `Stage 6 §5.3`; `decision-log §10/§11`; `workplan Stage 6`.
**Action — spec + epic.** Write the Epic-007 contract now (parameter shape into Curator, absent-data degrade path, solo-vs-party composition) so the seam's `fetch_readiness` has a defined consumer. Resolve "gates on the less-recovered" into concrete composition before Stage 8 party-merge.

### M12 — `heat_response` depends on an NWS historical-temp endpoint that likely doesn't exist
**What.** `Stage 6 §4.4` (S6-8) computes `heat_sensitivity` by fetching "NWS high temperature at the episode's representative point on the episode date" — a **historical** temperature for an arbitrary past date. The spec hand-waves "archived from the daily fetch, or re-fetched from `api.weather.gov/.../forecast/hourly`" — but `api.weather.gov` is a *forecast* service with no observation archive, and Rule #3 means the project keeps no weather archive to join against. The code already flags it: `belief_update.py:14` comment "heat_response inference (S6 §4.4 — NWS historical endpoint unconfirmed)"; S6-8 is 🔶.
**Why it matters.** `heat_response` is one of three capability beliefs and the only one needing a temporal weather join. If the source genuinely isn't available (likely — you'd need NCEI/ASOS/Meteostat, an unscoped dependency), the belief silently never promotes, and the degrade path ("skip, log, move on") **fails open and invisible** — the system never learns heat sensitivity with no signal that a whole belief class is dead. The "looks done, quietly does nothing" miss.
**Where.** `Stage 6 §4.4` (S6-8); `decision-log §31`; `belief_update.py:14`; Rule #3.
**Action — spec.** Resolve the source before building: (a) name a real observation archive (NCEI/ASOS/Meteostat) and accept a new adapter; **or (b, preferred)** capture temp at episode-ingest time from the same-day forecast/observation and store it **on the Episode** (a derived capability input, not a live overlay — Rule #3-compatible); or (c) cut `heat_response` from Phase 1 and mark it deferred. Don't ship a belief that depends on a phantom endpoint.

### m3 — Commons consent (T6) has no schema, surface, or epic — yet contributions are non-deletable

### m4 — Pace belief hardcoded to `pace_on_grade_moderate`, collapsing the grade-banded vocabulary

An easy valley walk and a strenuous climb both update "moderate" → a grade-blind average, exactly the conflation the vocabulary exists to prevent. When the Curator reasons "within your pace on a strenuous ridge," it reads a polluted number. **Action — fix or spec:** either band pace by the episode's grade (derive from ascent/distance) and key accordingly, or record in Stage 5 that Phase-1 intentionally uses a single moderate band, so vocabulary and code agree.
